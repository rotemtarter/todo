# תוכנית – Milestone 3: עריכת פרטים ומחיקת משימה

**מקורות:** `MILESTONES.md` (Milestone 3), `PRD.md` (זרימות 3 ו-6, FR-02, FR-05, FR-08, FR-10, Edge Cases), `ARCHITECTURE.md` (2.2–2.7, ADR-6, ADR-7, ADR-8, ADR-9, ADR-11, ADR-13), `DESIGN.md` (1.2, 1.4, 1.6, 2.3), `wireframes.png` (מסכי "דף הבית – משימה נבחרת", "אישור מחיקה", "מובייל").

**מטרה:** במשימה נבחרת השדות **כותרת**, **תיאור** ו-**תאריך יעד** ניתנים לעריכה מיד; **"שמור שינויים"** שומר במסד; **"מחק משימה"** פותח חלון אישור, ובאישור המשימה נמחקת מהשרת ומהרשימה.

**ללא שינוי במסד הנתונים:** הטבלה, ה-Constraints וההרשאות מ-Milestone 1 (כולל `update`/`delete` ל-`app_backend`) מספיקים. אין Migration חדשה, ולכן הדחיפה של אבן הדרך הזו לא תשנה את מבנה מסד ה-Production. אין Trigger ל-`updated_at`, ולכן ה-`UPDATE` יגדיר `updated_at = now()` בעצמו.

## 2. שרת

### 2.1 `api/tasks/[id]/index.ts`
1. המזהה מגיע מ-`req.query.id`. אם אינו UUID תקין ⇐ `400 INVALID_ID` ("הבקשה אינה תקינה"), בלי פנייה למסד.
2. Method: `PATCH` או `DELETE`; כל השאר ⇐ `405` עם `Allow: PATCH, DELETE`.
3. **`PATCH`:**
   - `readJsonObject` (אותן בדיקות כמו ביצירה: `415`/`413`/`400`, עד 16KB).
   - חובה ששלושת המפתחות `title`, `description`, `dueDate` יופיעו בגוף, כל אחד `string` או `null` (ADR-8); מפתח חסר או סוג אחר ⇐ `400`. שדות אחרים (`completed`, `position`, `id`) – מתעלמים.
   - `updateTaskDetails(id, input, todayInTimeZone(PRODUCT_TIME_ZONE))`.
   - הצלחה ⇐ `200` עם המשימה המעודכנת.
   - `TaskValidationError` ⇐ `422 VALIDATION_ERROR` עם `field` ו-`message` של השגיאה הראשונה.
   - `TaskNotFoundError` ⇐ `404 TASK_NOT_FOUND`, "המשימה לא נמצאה. ייתכן שנמחקה. רענן את הדף כדי לראות את הרשימה העדכנית."
   - כל שגיאה אחרת ⇐ `503`, "לא ניתן לשמור את השינויים כרגע. נסה שוב." (בלוג רק הודעת השגיאה, בלי תוכן המשימה).
4. **`DELETE`:**
   - אין גוף. `deleteTask(id)` ⇐ `204` בלי תוכן.
   - `TaskNotFoundError` ⇐ `404` (גם במחיקה כפולה, ADR-8).
   - אחרת ⇐ `503`, "לא ניתן למחוק את המשימה כרגע. נסה שוב."

### 2.2 `updateTaskDetails` – Transaction עם נעילת שורה (ADR-8)
באותו `client` מ-`BEGIN` עד `COMMIT`/`ROLLBACK`, **בלי** ה-Advisory Lock של הרשימה (עדכון פרטים אינו משנה את מבנה הרשימה):
```sql
begin;
select due_date from public.tasks where id = $1 for update;
-- אין שורה ⇒ rollback; throw TaskNotFoundError
-- validateTaskInput(input, today, savedDueDate) ⇒ שגיאה ⇒ rollback; throw TaskValidationError(errors)
update public.tasks
   set title = $2, description = $3, due_date = $4, updated_at = now()
 where id = $1
returning id, title, description, due_date, completed, position;
commit;
```
- ה-Validation רץ **בתוך** ה-Transaction מול התאריך השמור הנעול, כך שכלל "תאריך בעבר רק אם השתנה" נבדק מול הערך שבאמת יידרס.
- ה-`UPDATE` נוגע רק בשלושת שדות הפרטים וב-`updated_at` – לעולם לא ב-`completed` או ב-`position`.
- שתי שמירות מקבילות לאותה משימה מסודרות לפי נעילת השורה; האחרונה שמבצעת Commit קובעת (`last write wins`).

### 2.3 `deleteTask` – תחת נעילת הרשימה (ADR-8, ADR-13)
```sql
begin;
select pg_advisory_xact_lock($LIST_LOCK_KEY);           -- lockTaskList(client)
delete from public.tasks where id = $1 returning id;
-- אין שורה ⇒ rollback; throw TaskNotFoundError
-- נרמול המיקומים ל-0..N-1 לפי הסדר הקיים:
update public.tasks t
   set position = r.new_position
  from (select id, row_number() over (order by position, id) - 1 as new_position from public.tasks) r
 where t.id = r.id and t.position <> r.new_position;
commit;
```
- הנרמול שומר על הסדר הקיים ורק סוגר פערים (גם פערים שנוצרו ביצירות קודמות, ADR-13).
- כל השאילתות פרמטריות.

## 3. לקוח

### 3.1 `tasksClient`
- `updateTask(id, input)` – `PATCH /api/tasks/:id` עם `{title, description, dueDate}` (שלושתם תמיד); `200` ⇐ `Task`; אחרת `ApiRequestError` (כמו `createTask`).
- `deleteTask(id)` – `DELETE /api/tasks/:id`; `204` ⇐ הצלחה; אחרת `ApiRequestError`.
- כשל רשת ⇐ `ApiRequestError('network')` כמו היום.

### 3.2 `TaskDetails` – עריכה ישירה
- **מבנה (Wireframe "משימה נבחרת"):** כותרת האזור **"פרטי משימה"**; שדות **כותרת** (`input`), **תיאור** (`textarea`), **תאריך יעד** (`input type="date"`), עם אותם Placeholders כמו ב-Modal היצירה; מתחת – **"שמור שינויים"** (Primary) ו-**"מחק משימה"** (מסגרת וטקסט אדומים, לפי DESIGN 2.3). השדות פעילים מיד, בלי מצב "עריכה" נפרד. ללא בחירה – ההודעה הקיימת.
- **טיוטה:** State בתוך הקומפוננטה, מאותחל מהמשימה. `HomePage` מעביר `key={selectedId}`, כך שבחירה במשימה אחרת יוצרת קומפוננטה חדשה והטיוטה הקודמת נמחקת ללא התראה. מעבר לדף **אודות** או Refresh מסירים את הקומפוננטה – הטיוטה נמחקת. אין Local Storage.
  - בחירה חוזרת באותה משימה אינה מאפסת את הטיוטה (אותו `key`).
  - שינויים עתידיים ב-`completed`/`position` של המשימה הנבחרת (M4) לא ישנו את ה-`key`, ולכן לא יאפסו את הטיוטה – מוכן לדרישה של M4.
- **שמירה ("שמור שינויים"):**
  1. `validateTaskInput(draft, localToday(), task.dueDate)` – אותו כלל כמו בשרת: תאריך בעבר נחסם רק אם שונה מהתאריך השמור. שגיאה ⇐ הודעה ליד השדה (או בהודעה הכללית לשגיאת "כותרת או תיאור"), אין בקשה, הערכים נשארים.
  2. בזמן שמירה: "שמור שינויים" מציג "שומר…", ושני הכפתורים מושבתים (מונע שמירה כפולה או מחיקה באמצע שמירה).
  3. הצלחה ⇐ `onSaved(task)`: ב-`HomePage` מעדכנים במשימה **רק** את `title`, `description`, `dueDate` מתשובת השרת (ADR-9 – לא לדרוס `completed`/`position`). הטיוטה מתעדכנת לערכים המנורמלים שחזרו (למשל אחרי `trim`), ושורת הרשימה מציגה את הכותרת החדשה. מוצגת הודעה קצרה בירוק **"השינויים נשמרו"** (`role="status"`), שנעלמת בשינוי הבא בשדות.
  4. כישלון ⇐ הטיוטה נשארת בדיוק כפי שהוקלדה. `422` עם `field` ⇐ ליד השדה; `404` ושגיאות אחרות ⇐ הודעת השרת בהודעה הכללית; כשל רשת ⇐ "לא ניתן להתחבר לשרת. בדוק את החיבור לאינטרנט ונסה שוב." אפשר לנסות שוב.
- **שדה התאריך:** `min` = היום המקומי, כמו ביצירה. אם התאריך השמור כבר עבר, הוא עדיין מוצג כפי שהוא ונשמר בלי שינוי (הטופס עם `noValidate`, כך ש-`min` לא חוסם את השמירה). ניקוי התאריך – דרך בקר התאריך של Chrome.

### 3.3 `DeleteTaskModal` – אישור מחיקה (Wireframe "אישור מחיקה", DESIGN 1.4)
- Overlay כהה שקוף וחלון לבן קטן וממורכז: כותרת **"מחיקת משימה"**, השאלה **"האם אתה בטוח שברצונך למחוק את המשימה הזו?"**, כפתורים **"אישור"** (אדום – פעולת מחיקה) ו-**"ביטול"** (Secondary). בלי X (לא מופיע ב-Wireframe).
- נגישות: `role="alertdialog"`, `aria-modal`, `aria-labelledby`/`aria-describedby`; פוקוס התחלתי על **"ביטול"** (הבחירה הבטוחה); `Escape` = ביטול; בסגירה הפוקוס חוזר ל-"מחק משימה". לחיצה על הרקע לא סוגרת.
- **ביטול** ⇐ החלון נסגר, לא נשלחת בקשה, המשימה והטיוטה ללא שינוי.
- **אישור** ⇐ `deleteTask(id)`; בזמן הבקשה "אישור" מציג "מוחק…" ושני הכפתורים מושבתים.
  - הצלחה (`204`) ⇐ `onDeleted(id)`: ב-`HomePage` המשימה מוסרת מהרשימה, `selectedId = null`, והפרטים חוזרים ל-"בחר משימה מהרשימה כדי לצפות בפרטיה". הפוקוס עובר לכותרת הרשימה.
  - כישלון ⇐ החלון נשאר פתוח עם הודעת שגיאה בתוכו, המשימה **נשארת** ברשימה ובפרטים, ואפשר לנסות שוב או לבטל. ב-`404` – הודעת השרת (המשימה כנראה כבר נמחקה, יש לרענן).
- טיוטת עריכה שלא נשמרה **אינה** נשמרת לפני מחיקה; ביטול המחיקה משאיר אותה כמו שהיא.

### 3.4 עיצוב – `global.css`
- `.button--danger`: רקע לבן, מסגרת וטקסט `#EB5757`, Hover אדמדם בהיר; בחלון האישור – גרסה מלאה (רקע אדום, טקסט לבן) לכפתור "אישור".
- `.task-details__actions`: שני הכפתורים זה לצד זה, ברוחב שווה (כמו ה-Wireframe בדסקטופ ובמובייל).
- `.form-success`: טקסט ירוק `#27AE60` קטן.
- `.modal--small`: רוחב עד ~400px לחלון האישור; שאר עיצוב ה-Modal משותף עם חלון היצירה.
- הסרת עיצוב `[readonly]` שכבר לא בשימוש. הליטוש המלא נשאר ל-Milestone 5.

  - שינוי שדה ואז בחירה במשימה אחרת וחזרה ⇐ הערך המקורי (הטיוטה בוטלה).

### 4.2 Integration מול Dev – `npm run test:integration` (ADR-7, Snapshot ושחזור)
- `updateTaskDetails` משנה רק כותרת/תיאור/תאריך ו-`updated_at`; `completed = true` ו-`position` שהוגדרו מראש נשארים.
- תאריך שמור בעבר ללא שינוי ⇐ מצליח; שינוי לתאריך אחר בעבר ⇐ `TaskValidationError` והשורה ללא שינוי.
- מזהה שלא קיים ⇐ `TaskNotFoundError` בעדכון ובמחיקה.
- **שמירות מקבילות:** שני Pools שולחים עדכונים שונים לאותה משימה במקביל ⇐ שניהם מצליחים, הערך הסופי במסד הוא של אחד מהם בשלמותו (אין ערבוב שדות), ו-`completed`/`position` לא השתנו.
- `deleteTask` מוחק רשומה אחת ומנרמל מיקומים ל-0..N-1 בסדר הקודם (כולל רשימה עם פערים); מחיקה כפולה ⇐ `TaskNotFoundError`.
- מחיקה במקביל ליצירה (שני Pools) ⇐ אין מיקומים כפולים.

### 4.3 E2E ב-Chrome – `npm run test:e2e` (Desktop + Mobile, Snapshot של Dev)
- עריכת כותרת/תיאור/תאריך ושמירה ⇐ השורה ברשימה מתעדכנת; אחרי Refresh ובחירה – הערכים החדשים; במסד – הערכים החדשים.
- משימה עם תאריך יעד שמור בעבר (מוזנת ישירות למסד) ⇐ שינוי כותרת ושמירה מצליחים והתאריך נשאר; שינוי התאריך לתאריך אחר בעבר ⇐ הודעה ואין שינוי במסד.
- טיוטה שלא נשמרה ⇐ בחירת משימה אחרת וחזרה / מעבר ל"אודות" וחזרה / Refresh ⇐ הערך המקורי, בלי התראה.
- שגיאת שרת מדומה (`page.route` ⇐ `503`) ⇐ הודעה, הטיוטה נשארת; ביטול הדימוי ושמירה חוזרת ⇐ הצלחה.
- מחיקה: "ביטול" ⇐ המשימה נשארת (גם במסד); "אישור" ⇐ המשימה נעלמת, הודעת הבחירה מוצגת, והיא לא חוזרת אחרי Refresh.
- מחיקה עם שגיאת שרת מדומה ⇐ המשימה נשארת ברשימה ובמסד, והודעה מוצגת.
- משימה שנמחקה בינתיים (מחיקה ישירה במסד אחרי הטעינה) ⇐ שמירה מציגה את הודעת ה-`404`.
- שתי בקשות `PATCH` מקבילות ישירות ל-API ⇐ ערך אחד שלם נשמר; `completed`/`position` לא השתנו.
- כל בדיקות ה-E2E של M1–M2 ממשיכות לעבור (עם העדכון ב-`tasks-view.spec.ts`).

## 6. החלטות מימוש קטנות (לאישורך במסגרת אישור התוכנית)

1. **הודעת הצלחה** קצרה בירוק, "השינויים נשמרו", אחרי שמירה (DESIGN 2.3 מתיר משוב הצלחה בירוק). בלעדיה אין שום חיווי שהשמירה הצליחה.
2. **שגיאת מחיקה מוצגת בתוך חלון האישור**, שנשאר פתוח לניסיון חוזר או ביטול.
3. **מחיקה של משימה שכבר נמחקה (`404`)** – מוצגת הודעה "המשימה לא נמצאה... רענן את הדף", והמשימה **לא** מוסרת מהתצוגה עד רענון (לפי ARCHITECTURE 2.6: "UI מציג שגיאה ורענון יכול לתקן את המצב").
4. **פוקוס התחלתי בחלון האישור על "ביטול"**, כדי ש-Enter בטעות לא ימחק.
5. **כפתור "אישור" אדום** (פעולת מחיקה לפי ה-Style Guide), אף שב-Wireframe האפור הוא כהה; "מחק משימה" באזור הפרטים – מסגרת אדומה.
6. **"שמור שינויים" תמיד זמין** (גם בלי שינוי) – שמירה ללא שינוי אינה מזיקה, וזה פשוט יותר מזיהוי "יש שינויים".
7. **נוסחי הודעות** שאינם מוגדרים ב-PRD – כמפורט בסעיפים 2.1 ו-3.2–3.3.

אם במהלך הבנייה תתקבל החלטה טכנית משמעותית שאינה מכוסה ב-ADR-8/ADR-9/ADR-13, היא תתועד כ-ADR-14 ב-`ARCHITECTURE.md`.
